# 发布前验证：从 0.4.3 同步遗漏中吸取的经验

## 为什么漏检

0.4.3 的本地前端、Rust 和打包检查确实执行并通过，但测试未覆盖“旧文件快照仍引用后来被删除的词汇”。由当前数据库生成的快照不会包含已经级联删除的 occurrence，正常往返恢复测试因此不能暴露这个历史状态。错误转换测试覆盖了 SQLite 等异常，却漏掉实际协议错误码穿过原生同步边界的情况，导致问题被误报为本机写入失败。

安装包 Actions 另外只有编译、签名和上传步骤，没有依赖单元测试。原 CI 在 main 推送和 PR 上运行，不能作为手动分支安装包的必经检查。这是流程薄弱点；直接原因仍是历史场景缺少测试，而非多跑一次已有测试就能发现。

## 自动检查已经落实

- `npm run check:release:tests` 统一执行 lint、全部前端测试、前端构建、原生资源准备和 `cargo test --lib --locked`。
- 本地完整 `npm run check:release` 调用同一套关卡，然后继续 macOS release 程序和 Android APK 构建。
- Build Installers 的三个平台 job 都依赖 `release-checks`。任何回归失败，安装包编译、签名、上传不会开始。
- Actions 的 platform 选择 `checks` 可只验证关卡，不产生安装包、不更新 Release。检查和后续安装包来自同一提交。
- 冻结的合成 `library-snapshot-v1.json` 不由当前序列化器重新生成，保留缺少新字段的旧格式。测试同时覆盖旧/当前事件版本、明确删除的单词和词组、身份别名、保留正文与翻译、不复活删除数据、真正未知引用仍拒绝，以及失败回滚和错误代码保真。

## 后续按变化补验收

同步、存储、删除、迁移或账号代码变更，应检查历史状态，而非只检查全新安装：旧格式、删除后恢复、别名合并、重复重试、失败中断与回滚。新增失败场景先保留一个可重复、无真实用户资料的回归样例；不要只凭提示文案判断根因。

涉及同步下载/分块/登录时，还需用测试账号验证真实服务：下载、解密、应用、续期、断点续传及重新同步。单元测试没有验证远端当前部署、凭据和网络；本机资料只在授权后通过副本诊断，不作为 CI 样例。

涉及 UI 时，继续按 AGENTS.md 验收默认和 midnight 主题、桌面/移动端及 hover、selected、disabled、键盘焦点等状态。当前发布关卡没有宣称替代 UI 截图验收或真实设备操作。

发布结果分别写明自动回归、平台打包、真实服务/设备操作哪些通过、哪些未执行。安装包构建成功不等同于云端全量同步成功，也不等同于所有旧数据组合都已覆盖。
